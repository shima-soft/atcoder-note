問題を読み解く

行を黒く塗る・列を白く塗る — 黒マスの数を毎回答える

▶ 動画 0:00〜（オープニング）・1:30〜（問題解説）
同じ行や列が何度も塗り直される。「後から塗った色で上書き」がこの問題の主役です。

問題文（噛み砕き版）

N×N のグリッドがあり、最初は全マス白。Q 個のクエリを順番に処理します。

  • 1 R … 上から R 行目を全部黒に塗る
  • 2 C … 左から C 列目を全部白に塗る

各クエリの処理が終わるたびに、グリッド内の黒いマスの個数を出力します。

出典: AtCoder ABC461 E - E-liter（配点 475 点 / 実行時間制限 2 秒）

制約

  • N … グリッドの一辺（1 以上 3×10⁵ 以下）
  • Q … クエリの個数（1 以上 3×10⁵ 以下）
  • R, C … 塗る行・列の番号（1〜N）

⚠️ マスの総数は最大 3×10⁵ × 3×10⁵ = 9×10¹⁰ 個。グリッドをそのまま配列で持つのは不可能という強いヒントです。

入出力例（例1: N=3、4 クエリ）

クエリ意味黒マス数
1 11行目を黒に3
1 33行目を黒に6
2 22列目を白に4
1 11行目をもう一度黒に5

3つ目で 1・3 行目の黒が 1 個ずつ消えて 6−2=4。4つ目は白かった 1 マスだけ黒に戻って 4+1=5。
例2: 真っ白なグリッドの列を白く塗っても 0 のまま。

📝 理解度セルフチェック

Q1. クエリ「2 C」で黒マスが増えることはある？

A1. ない。白く塗る操作なので黒マスは減るか変わらないかのどちらか。

Q2. 制約から読み取れる「禁止事項」は？

A2. マスの総数が最大 9×10¹⁰ 個なので、グリッドを二次元配列でそのまま持つこと（メモリ的に不可能）。

失敗アプローチ

なぜ「グリッドをそのまま作る」はダメなのか？

▶ 動画 3:30〜
マスは最大 9×10¹⁰ 個。作るだけでメモリも時間も足りない — 制約が「マス単位で扱うな」と教えてくれます。

⚠️ ありがちな失敗

  • N×N の二次元リストを作る → 作った瞬間に MemoryError
  • クエリごとに全マスを数え直す → 1 回 O(N²) で即 TLE

⏱ 数の感覚: Python が 1 秒にこなせるのは約 10⁷ 回。9×10¹⁰ 回はおよそ 9,000 秒 — 制限 2 秒の 4,500 倍です。

✅ 正解への気づき: マスを 1 個ずつ管理しない — 行・列単位で考える。行と列が覚えるのは「最後に塗られた時刻」だけでいい。

気づき①

マスの色は「行と列、どちらが後に塗られたか」で決まる

▶ 動画 5:00〜
グリッドの代わりに、行と列の「最後に塗られた時刻」だけを覚える — メモリは O(N) で済みます。

💼 身近な例え

共有ファイルの上書き保存と同じ。誰が何を書いても、最後に保存した内容だけが残ります。

  • 覚える配列は row_time と col_time の 2 本だけ — メモリ O(N)
  • 塗り直しは「時刻を新しい値に書き換える」だけで O(1)
  • 時刻はクエリ番号 t（1, 2, 3, …）。「まだ一度も塗られていない」は時刻 0 として扱う
📝 理解度セルフチェック

Q1. row_time[r]=4、col_time[c]=9 のとき、マス (r, c) の色は？

A1. 白。列の白塗り（時刻9）の方が行の黒塗り（時刻4）より後だから。

Q2. 一度も塗られていない行と列が交差するマスの色は？

A2. 白。両方とも時刻 0 で「行の時刻 ＞ 列の時刻」が成り立たないため、初期状態の白のまま。

気づき②

総数は数え直さない — 増減だけを足し引きする

▶ 動画 7:00〜
変わるのは「いま塗った 1 行・1 列」だけ。そこで増えた数・減った数だけ合計に反映します。

📐 増減の式

  • 行 R を黒に → 行はまるごと黒になる: 増加 = N −（直前にその行で黒かった数）
  • 列 C を白に → 列はまるごと白になる: 減少 =（直前にその列で黒かった数）

✅ 「直前に黒かった数」も時刻で分かる:

  • 行 R の黒マス数 = 行 R の時刻より前に白塗りされた列の本数（行の黒が上書きして勝っている分）
  • 列 C の黒マス数 = 列 C の時刻より後に黒塗りされた行の本数（列の白の上に塗られた分）

⚠️ ただし毎回全行・全列を見て数えると 1 回 O(N) — 合計 9×10¹⁰ 回で TLE。高速に数える道具が必要 → 次の BIT へ。

📝 理解度セルフチェック

Q1. 黒い行をもう一度黒く塗ったとき、増加分はいくつ？

A1. その行で白かったマスの数だけ増える。全部黒のままなら増加 0（N − N = 0）。

Q2. サンプル1の 3 つ目のクエリで「−2」になった理由は？

A2. 2 列目で黒かったのは 1 行目と 3 行目の 2 マスだけだったから。

道具を選ぶ

「時刻◯より前は何本？」を BIT で一瞬で数える

▶ 動画 9:00〜
BIT は「件数の追加・削除」と「先頭からの累計」を両方 O(log Q) でこなす集計表です。

💼 身近な例え: 売上台帳の小計欄

日付ごとの件数に小計を付けておけば「◯日までの累計」が一瞬で答えられる。BIT はその台帳のデータ構造版です。

  • ある時刻の件数を +1 / −1 する（塗り直し＝古い時刻を −1、新しい時刻に +1）— O(log Q)
  • 先頭からある時刻までの累計を出す — O(log Q)
  • 本問では行用と列用の 2 本を用意。「時刻 t より後」は「全体 N − 時刻 t までの累計」で求める
📝 理解度セルフチェック

Q1. 列2（時刻5）をもう一度白く塗った（新しい時刻9）。BIT への操作は？

A1. 時刻5の件数を −1、時刻9の件数を +1（時刻の引っ越し）。

Q2. 「時刻 t より後に黒塗りされた行の本数」を式で書くと？

A2. N − bit_sum(row_bit, t)。全体から「時刻 t まで」の累計を引く。

コード①

入力と BIT（時刻カウント表）の準備（20 行）

▶ 動画 11:00〜
行用と列用、2 本の BIT を用意する。中身は「足す・引く・累計を出す」の 3 機能だけ。
abc461_e.py（前半） 
import sys
input = sys.stdin.readline

N, Q = map(int, input().split())
size = Q + 2
row_bit = [0] * (size + 1)
col_bit = [0] * (size + 1)

def bit_add(bit, i, x):
    i += 1
    while i <= size:
        bit[i] += x
        i += i & (-i)
def bit_sum(bit, i):
    i += 1
    s = 0
    while i > 0:
        s += bit[i]
        i -= i & (-i)
    return s

🔍 それぞれの役割

  • row_bit ＝ 行を黒く塗った時刻の集計表 / col_bit ＝ 列を白く塗った時刻の集計表
  • bit_add(表, 時刻, x) … その時刻の件数を x だけ増減
  • bit_sum(表, 時刻) … 時刻 0〜t の累計件数を返す
  • 時刻は 0〜Q を使うので表の長さは Q + 2 で確保。冒頭の i += 1 は「時刻 0」も表で扱うためのずらし（BIT は 1 始まり）
  • i & (-i) は 2 進数で「担当ブロック」を渡り歩くテクニック。仕組みは後回しで OK、使い方を覚えるのが先
コード②

クエリ処理 — 増減を足し引きして即出力（20 行）

▶ 動画 13:00〜
「前回時刻 old を調べる → 今の黒マス数を BIT で出す → 時刻を t に引っ越す」が両クエリ共通の型です。
abc461_e.py（後半） 
row_time = [0] * (N + 1)
col_time = [0] * (N + 1)
bit_add(row_bit, 0, N)
bit_add(col_bit, 0, N)
total = 0
for t in range(1, Q + 1):
    typ, x = map(int, input().split())
    if typ == 1:
        old = row_time[x]
        total += N - bit_sum(col_bit, old - 1)
        bit_add(row_bit, old, -1)
        bit_add(row_bit, t, 1)
        row_time[x] = t
    else:
        old = col_time[x]
        total -= N - bit_sum(row_bit, old)
        bit_add(col_bit, old, -1)
        bit_add(col_bit, t, 1)
        col_time[x] = t
    print(total)

🔍 処理の流れ

  • 行を黒に（typ == 1）: 今の黒マス数 = bit_sum(col_bit, old - 1)（時刻 old より前に白塗りされた列の本数）。total += N − 黒マス数 で増加分を加算
  • 列を白に（else）: 消える黒 = N - bit_sum(row_bit, old)（時刻 old より後に黒塗りされた行の本数）
  • どちらも最後に時刻の引っ越し: old の件数を −1、t に +1
  • 初期値は「全行・全列が時刻 0」— だから最初に時刻 0 へ N 件ずつ登録

⏱ 計算量: 1 クエリ O(log Q) × Q 回 = O(Q log Q) ≈ 540 万回。O(N log N) 級は N ≤ 5×10⁵ が目安 → Q = 3×10⁵ なら Python でも間に合う（不安なら PyPy 提出）。

まとめ

解法パターンの整理

▶ 動画 15:00〜
「上書きは最後の時刻だけ持つ」「総数は増減で更新」「時刻の集計は BIT」— 3 点セットで覚えましょう。

1. 後勝ちの整理

行の黒と列の白が重なったら、後に塗った方が勝つ。だからマスを覚える必要はなく、行・列の「最後に塗られた時刻」（row_time / col_time）だけ持てばよい。メモリは O(N) で済む。

2. 総数は増減だけ更新

毎回数え直すと O(N) × Q 回で破綻。行を黒に: +（N − 今の黒マス数）、列を白に: −（今の黒マス数）。変化した 1 行・1 列の差分だけを合計に反映する。

3. 時刻の集計は BIT

「時刻◯より前／後に塗られた本数」を O(log Q) で数える集計表。足す・引く・累計の 3 操作だけで、全体 O(Q log Q) ≈ 540 万回。Q = 3×10⁵ でも Python で間に合う。

🔁 今日の解法パターン（上書き系クエリの定石）

グリッドは作らない → 行・列の最後の時刻だけ記録 → 総数は増減だけ更新 → 時刻の集計は BIT → O(Q log Q) で完答

「最終更新がいつか」さえ持っていれば最新状態は判定できる — 在庫表や顧客リストの更新履歴と同じ発想です。

クエリ query

Wikipedia: クエリ 🔗
O 記法 オーきほう / Big-O notation
