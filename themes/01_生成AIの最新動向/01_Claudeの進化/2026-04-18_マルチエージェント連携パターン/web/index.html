INTRO

マルチエージェントとは？

AIが「チームを組んで」役割分担しながら複雑な仕事を片づける仕組み ⏱ 0:00〜

一言で

1体のAIではなく、専門の複数AIが協力することで、速くて正確な仕事が実現する

1
複雑なタスクを分解できる
長大・多工程の作業を細かなステップに分けて各AIが担当
2
並列処理で大幅な高速化
互いに依存しない作業を同時進行し、単体AIより処理時間が激減
3
専門AIで品質向上
生成・検証・調査など得意領域に集中させることで精度が上がる
▶
今日のゴール
5つのパターンを知り、場面に応じて使い分けられるようになる
💡 理解度チェック
マルチエージェントが注目される3つの理由を答えてみてください。▼
①複雑なタスクの分解、②並列処理による高速化、③専門AIによる品質向上。単体AIでは難しい大規模・複雑な仕事をチームで実現できます。
GUIDE

パターン選択の3つの鉄則

「洗練度」ではなく「目的適合性」でパターンを選ぶ ⏱ 3:00〜

1
シンプルから始める
最も単純なパターンを選び、課題が見えてから複雑な構成に移行する。最初から凝った設計は不要。
2
観察してから進化させる
実際の失敗・ボトルネックを観察し、必要になったときだけ構成をアップグレードする。
3
洗練度で選ばない
複雑なパターンは「より良い」わけではない。目的・コスト・チームの理解度に合った選択が最善。
PATTERN 01

Generator-Verifier

「作る係AI」と「チェックする係AI」の2人1組 ⏱ 4:30〜

一言で

生成と検証を分離することで品質保証ループを自動化する

💼 実務例: カスタマーサポートメール
1

Generator AIが返信メールを下書き

2

Verifier AIがナレッジベースと照合しNGワード検出

3

OKなら送信、NGなら修正ループ

✅ 使えるシーン
  • コード生成（書く＋テスト実行）
  • ファクトチェック・ルーブリック採点
⚠️ 失敗パターン
  • 検証基準が曖昧 → チェックが機能しない
  • ループ上限なし → コスト爆発
💡 理解度チェック
Generator-Verifierを機能させるために「必ず設定すること」は何ですか？▼
①明確な検証基準（Verifierが何をどう確認するかを定義する）と、②ループの上限回数（無限修正を防ぐ）の2つが必須です。
このパターンが特に得意とする業務を1つ挙げてください。▼
コード生成（一方が書き、もう一方がテスト実行）が典型的な強みです。他にもファクトチェックやルーブリック採点が向いています。
PATTERN 02

Orchestrator-Subagent

「司令塔AI」が全体を計画し、「部下AI」たちに専門仕事を割り振る階層型 ⏱ 6:30〜

一言で

指揮者AIがタスクを分解し、専門AIに委任して結果を統合する

💼 実務例: コードレビューシステム
1

Orchestratorがコードを3タスクに分解

2

セキュリティ・テスト・スタイルのAIが並列チェック

3

Orchestratorが結果を統合し総合レポート出力

✅ 使えるシーン
  • タスクを独立したサブ作業に分解できる場合
  • 専門領域ごとに異なるAIを割り当てたい場合
⚠️ 失敗パターン
  • 情報ボトルネック: 各AIの発見が他に届かない
  • Orchestratorが単一障害点になりうる
💡 理解度チェック
Orchestratorパターンで発生しやすい「情報ボトルネック」とはどういう問題ですか？▼
セキュリティAIが発見した問題を、テストAIは知らないまま作業を進めてしまうような状態です。各Subagentの発見がOrchestrator経由でしか共有されないため、並列で動く他のAgentに伝わりません。
PATTERN 03

Agent Teams

共有タスクキューからAIが自律的にタスクを取り出す並列処理型 ⏱ 8:30〜

一言で

指揮者なしで、複数のAIが共有キューから仕事を取り出して独立処理する

💼 実務例: フレームワーク移行プロジェクト
1

「100サービスを移行」タスク群をキューに積む

2

各WorkerがキューからPickUp → 独立して処理

3

完了したWorkerは次のタスクを自動取得して続行

✅ 使えるシーン
  • 互いに依存しない大量の均質タスクを一気に処理
  • 長期運用で各AIが経験を積み改善が期待できる場合
⚠️ 失敗パターン
  • タスク分割ができていない → 複数AIが競合
  • 中間結果の共有が必要な場合は別パターンが向く
💡 理解度チェック
Agent Teamsパターンが最も力を発揮する「タスクの特徴」は何ですか？▼
互いに依存しない（独立した）大量の均質タスクが得意です。各WorkerがそれぞれのタスクをPickUpして並列処理できるため、大規模なバッチ処理や移行作業に最適です。
PATTERN 04

Message Bus

イベントを「掲示板」に投稿し、興味あるAIだけが反応するイベント駆動型 ⏱ 10:30〜

一言で

疎結合なPub/Sub設計で、AIの追加・変更が既存の配線に影響しない

💼 実務例: セキュリティ運用センター
1

ネットワーク異常AIがイベントをBusにPublish

2

購読中の調査AIとインシデントAIが自動起動

3

新AIを追加しても既存AIへの影響ゼロ

✅ 使えるシーン
  • イベント発生をトリガーに複数AIを動かしたい場合
  • AIの追加・変更を頻繁に行う拡張性重視の構成
⚠️ 失敗パターン
  • サイレント障害: イベントが消えても誰も気づかない
  • 連鎖的なイベント発火でデバッグが困難になる
💡 理解度チェック
Message Busの「疎結合」とは何を意味していますか？▼
AI同士が直接つながっていないことを意味します。PublisherはどのSubscriberが見ているか知らなくてよく、新しいAIを追加する際に既存の接続を書き換える必要がありません。
PATTERN 05

Shared State

全AIが「共有ノート」に読み書きして中央管理なしで協力する ⏱ 12:30〜

一言で

共有ストアを通じたリアルタイム情報共有で、単一障害点のないAIチームを実現

💼 実務例: 市場調査レポート自動生成
1

各調査AIが独立して情報収集しStoreに書き込み

2

他のAIの書き込みを参照しながら調査を深掘り

3

統合レポートAIがStore全体を読み込み報告書生成

✅ 使えるシーン
  • 各AIがリアルタイムに互いの発見を参照したい場合
  • 高可用性が必要で単一障害点を排除したい構成
⚠️ 失敗パターン
  • 終了条件がない → 無限ループ・コスト爆発
  • 同じ調査の重複実行でコストが膨らむ
💡 理解度チェック
Shared Stateパターンで「終了条件」の設計が重要な理由は？▼
誰かが書き込むと他のAIが反応して書き込み、さらに別のAIが反応…という連鎖が起きやすいからです。「N件書いたら終了」「フラグが立ったら終了」など明確な終了条件がないと無限ループになります。
COMPARE

5パターン 比較表

連携方式・強み・限界・最適用途を一覧で確認 ⏱ 14:00〜

パターン 連携方式 強み 主な限界 最適な用途
Generator-Verifier 生成 → 検証 → ループ 品質保証・精度向上 検証基準が必要・ループ上限必須 コード生成＋テスト、ファクトチェック
Orchestrator-Subagent 階層的な委任・統合 タスク分解・専門化 情報ボトルネック・単一障害点 コードレビュー、複雑な分析
Agent Teams 共有キューから自律取得 大規模並列処理 厳密なタスク分割が必要 大規模マイグレーション、一括変換
Message Bus Pub/Sub イベント駆動 疎結合・拡張性 サイレント障害・デバッグ困難 セキュリティ監視、リアルタイム通知
Shared State 共有ストアの読み書き 単一障害点なし 重複作業・無限ループリスク リサーチ統合、知識ベース構築

まとめ

5つのパターンは「ツールボックス」— 目的に合わせて選ぶのが正解 ⏱ 16:00〜

1
AIチームは「役割分担」で真価を発揮
1体に任せるより専門AIが協力する方が速くて正確。マルチエージェントはその設計思想。
2
最初はシンプル → 観察 → 進化
パターンの複雑さは「良さ」ではない。Generator-Verifierから始め、必要に応じて進化させる。
3
5つのパターンを使い分けが鍵
それぞれに得意な場面がある。フローチャートを参考に「自分のタスク」に合う一手を選ぼう。

用語解説

このシリーズで登場した用語の読み方と概要

Anthropic アンソロピック anthropic.com 🔗

Claudeを開発した米国のAI安全研究企業（2021年設立）。本記事の発行元。

Claude クロード claude.ai 🔗

AnthropicのAIアシスタント。マルチエージェントシステムのベースAIとして活用できる。

LLM エル・エル・エム

Large Language Model（大規模言語モデル）。ChatGPT・Claudeなどの中核技術で文章を理解・生成するAI。

マルチエージェント Multi-Agent

複数のAIエージェントが役割分担しながら協力して目標を達成する設計手法。

Orchestrator オーケストレーター

「指揮者」役のAI。タスク全体を計画し各Subagentに仕事を割り振って結果を統合する。

Subagent サブエージェント

Orchestratorから委任を受けて特定の専門タスクをこなすAI。「部下」にあたる存在。

Generator ジェネレーター

コンテンツ・コードなどを生成する担当AI。Verifierとペアで品質を高めるために使われる。

Verifier ベリファイアー

Generatorの出力を基準に照らして検証するAI。「校正・品質チェック」担当にあたる。

Message Bus メッセージバス

AIエージェント間のイベント・メッセージを仲介するルーター。掲示板に書いて他のAIが受け取るイメージ。

Pub/Sub パブサブ

Publish（投稿）とSubscribe（購読）の仕組み。Message Busの基盤技術。SNSのフォロー機能に近い。

Agent Teams エージェント・チームズ

共有タスクキューから複数のWorker AIが自律的にタスクを取り出し並列処理するパターン。指揮者不在で大規模処理に強い。

Shared State シェアード・ステート

全AIが共有の「ノート（State Store）」に読み書きしながら協調するパターン。単一障害点がなくリアルタイム情報共有が可能。
